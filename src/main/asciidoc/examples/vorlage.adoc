== Einleitung

[TIP]
====
Die Einleitung enthält die Systemidee und umfasst maximal eine Seite Text. Sie entspricht dem Produktkarton des Softwaresystems und enthält eine einheitliche Sicht von Auftraggeber, Fachbereich und Entwicklungsteam.
====

== Architektur Überblick

[TIP]
====
Beschreibt die Einordnung des zu spezifizierenden Systems in die Anwendungslandschaft des Auftraggebers. Die Nachbarsysteme werden identifiziert, die Datenquellen und die Datensenken werden dargestellt. Das zu spezifizierende System wird grob in Teilsysteme gegliedert, wobei sich diese Gliederung i.d.R. an der Fachlichkeit orientiert. Die systemeigene Datenhaltung wird skizziert. Weiter werden gesetzte technische Randbedingungen an das System (Host, Web-Client, vorhandene Middleware, Datenbanksysteme, Programmiersprachen) erhoben und dokumentiert. Aus dieser ersten Architektursicht wird in der Phase der Konstruktion die technische Systemarchitektur entwickelt. Da das Vorgehen zur Dokumentation der Architektur größtenteils erst in der Vorlesung Softwarearchitektur besprochen wird, enthält dieser Abschnitt zunächst nur das Systemkontextdiagramm.
====

== Rollen

[TIP]
====
Der nutzende Personenkreis eines Softwaresystems ist vielfältig, d.h. den einen Benutzertyp gibt es nicht. Folgende Merkmale sollten untersucht werden, um Rollen zu finden:

- Rechte pro Benutzergruppe
- Verschiedene Perspektiven auf das Softwaresystem
- Häufigkeit, mit der das Produkt benutzt wird
- Vertrautheit mit dem fachlichen Gebiet (Neuling, Profi)
- Generelles Verständnis von Computern und Programmen (Neuling, Profi)
- Verständnis von dem eigentlichen Produkt
- Motivation für die Produktnutzung
====

== Anwendungsfälle

[TIP]
====
Ein Anwendungsfall ist die Beschreibung einer Abfolge von zielgerichteten Interaktionen zwischen Akteuren und einem System. Anwendungsfälle beschreiben das extern sichtbare Systemverhalten in der Sprache und aus der Sicht der Personen, die das System nutzen. D.h. für diese Personen wird durch einen Anwendungsfall beschrieben, wie durch das System ein  sinnvoller Dienst erbracht oder ein benutzbares Ergebnis erreicht werden kann.

Ein Anwendungsfall besteht aus einer oder mehreren systemunterstützten Aktivitäten. Ein Akteur ist eine außerhalb des Systems agierende beteiligte Person, die an der in einem Anwendungsfall beschriebenen Aktivität beteiligt ist. Akteure nehmen in der Interaktion gewöhnlich eine definierte Rolle ein: Es sind diejenigen Personen, die das System oder andere Systeme benutzen. Die Anwendungsfälle werden jeweils in einem eigenen Abschnitt beschrieben. Zur Verbesserung der Übersicht werden alle Anwendungsfälle in einem Anwendungsfalldiagramm dargestellt. Wenn möglich, werden die Anwendungsfälle dabei fachlich gruppiert.

====

==== Standardablauf

[TIP]
====
Ein Ablauf zeigt das Zusammenspiel zwischen Akteur und System. Typischerweise wechselt sich der Akteur immer mit dem System ab. Erst führt der Akteur eine Aktion aus, dann reagiert das System darauf, usw. Ein Ablauf hat keine Verzweigungen. Sind diese erforderlich, so werden diese über alternative Abläufe oder Fehlerfälle abgebildet.

====

. Der Akteur macht etwas.
. Das System reagiert auf den Akteur.

[TIP]
====
Zur Verdeutlichung eines Ablaufs kann ein UML Aktivitätsdiagramm verwendet werden.
====

==== Name alternativer Ablauf 1

[TIP]
====
Eine Alternative zum Standardablauf: dabei werden einzelne Schritte ersetzt (oder nicht durchgeführt).

====

. Der Akteur macht etwas anderes.
. Das System reagiert wieder auf den Akteur.

==== Name Ablauf Fehlerfall 1

[TIP]
====
Eine Fehlersituation im Standardablauf: dabei werden einzelne Schritte ersetzt (oder nicht durchgeführt).
====

. Der Akteur macht etwas, das einen Fehler hervorruft.
. Das System zeigt eine Fehlermeldung an oder gibt einen Verbesserungsvorschlag.

[TIP]
====
Statt viele Fehlerabläufe zu spezifizieren, sollten Anwendungsfälle so gestaltet sein, dass Fehler gar nicht erst auftreten können.
====

==== Übersicht der Abläufe

[TIP]
====
Um Abläufe zu visualisieren, bzw. mehrere Abläufe gemeinsam darzustellen, können diese mit einem UML Aktivitätsdiagramm
dargestellt werden. Nur bei komplexeren Abläufen liefert so ein Diagramm einen Mehrwert.
====

== Dialoge

[TIP]
====
Beschreibt das statische Aussehen (Layout) und das dynamische Verhalten der Benutzerschnittstelle des Systems. Das statische Aussehen wird durch Mockups und Angaben zum angezeigten Entitätstyp bzw. zu Attributen beschrieben. Das dynamische Verhalten wird durch textuelle Beschreibungen und ggf. durch Interaktionsdiagramme (UML Zustandsdiagramme) beschrieben. Damit werden auch die Transaktionsgrenzen verdeutlicht, d.h. es wird klargemacht, wann die Eingaben des Benutzers persistent sind. Durch die Angabe der angezeigten Entitätstypen und ggf. angezeigten Attribute wird in der Spezifikation eine Verbindung zwischen Benutzerschnittstelle und Datenmodell hergestellt. Durch eine Benennung der Anwendungsfälle, die durch diese Benutzerschnittstelle unterstützt werden, wird die Verbindung zur funktionalen Spezifikation mittels Anwendungsfällen hergestellt.

== Schnittstellen

[TIP]
====
Beschreibt die Verbindung zwischen dem spezifizierten System und den externen Nachbarsystemen, mit denen dieses System kommuniziert. Die externen Systeme werden benannt. Es wird spezifiziert, welche Daten ausgetauscht werden oder welche externen Dienste benutzt werden. Es werden die Anwendungsfälle aufgeführt, bei denen externe Systeme benutzt werden.

Aus Sicht des eigenen Systems kann es abstrakte Schnittstellen geben, über die mehr als ein externes System angebunden werden kann. In diesem Fall zerfällt die Spezifikation der Nachbarsystem-Schnittstelle in zwei Teile:

- Definition der Anforderungen des eigenen Systems an die Schnittstelle: Welche Daten werden erwartet bzw. bereitgestellt?
Welche Dienste werden benutzt bzw. geboten?
- Beschreibung der konkreten Anbindung des Nachbarsystems: Wie passen die oben spezifizierten Anforderungen mit dem konkreten Nachbarsystem zusammen? Wie werden die Datenstrukturen aufeinander abgebildet? Welche konkreten Dienste des Nachbarsystems werden genutzt?

Beispiel: Abstrakte Schnittstelle zu einem Nachbarsystem "Abrechnungssystem"; konkrete Schnittstelle zu einem Nachbarsystem "XYZ".

Bei der Beschreibung der Schnittstellen können wir zwischen verschiedenen Arten von Schnittstellen unterscheiden:

- offline-Schnittstelle mit Datenaustausch über Dateiablage oder ähnliche Verfahren
- online-Schnittstelle mit direktem Zugriff auf die Datenbank des Nachbarsystems (oder umgekehrt: Nachbarsystem greift auf die Datenbank des eigenen Systems zu)
- online-Schnittstelle mit direktem Aufruf von Diensten des Nachbarsystems

====

== Migration

[TIP]
====
Beschreibt in detaillierter Form, wie bei Ablösung eines Altsystems die Daten aus dem Altsystem in das neue System überführt werden. Es handelt sich dabei um eine Datenmigration, die i.a. einmalig bzw. stufenweise stattfindet. Werden Teile eines Altsystems (zeitweise) zu einem Nachbarsystem und müssen Schnittstellen zu diesem System bereitgestellt werden, so werden diese Schnittstellen im Baustein Nachbarsystem-Schnittstellen beschrieben.
====

== Glossar

[TIP]
====
Ein Glossar enthält Definitionen wichtiger Begriffe des Projekts. Dies umfasst fachliche, a ber auch technische Begriffe.
Eine solche zusammenfassende Übersicht ist fachlich oder alphabetisch geordnet. Damit wird eine begriffliche Grundlage geschaffen, die sicherstellt, dass alle dasselbe meinen, wenn sie dieselben Begriffe verwenden. Ein solches Glossar ist insbesondere dann wichtig, wenn schon die Kundenvertreter untereinander keine klare und einheitliche Begriffswelt haben.
